Critical Security Findings

P0 issues requiring immediate remediation before production deployment

Security Finding Severity Distribution
  • CRITICAL-01 Plaintext Password Exposure via Multiple Vectors P0 · Auth

    Platform credentials are stored with Fernet encryption, but the crypto.py encrypt function silently passes empty strings through without encryption. More critically, _safe_decrypt() in platform_service.py implements a plaintext fallback path — if decryption fails for any reason, it returns the original (potentially plaintext) value. This means a corrupt or missing Fernet key results in raw plaintext passwords being returned.

    The AuditMiddleware logs full request bodies including sensitive data. Fields like auth_token, bearer, and session_key are not present in the _SENSITIVE_FIELDS set, allowing tokens and keys to be written to audit logs in plaintext.

    Files: backend/app/core/crypto.py, backend/app/services/platform_service.py, backend/app/middleware/audit.py

  • CRITICAL-02 Shell Command Injection in Operation Executor P0 · Injection

    operation_executor.py constructs shell commands using Python f-strings and executes them with subprocess.run(command, shell=True, ...). User-controlled parameters (e.g., target hostnames, VM names) are interpolated directly into the command string. The validation regex ^[a-zA-Z0-9][a-zA-Z0-9._-]*$ allows underscores in hostnames (non-RFC compliant, but common in internal networks) yet does not prevent shell metacharacters like backticks, $(), or semicolons when combined with other bypass techniques.

    Impact: An authenticated user with operation execution privileges could achieve remote code execution on the backend server by crafting a malicious target parameter. The shell=True flag passes the command through /bin/sh -c, enabling full shell interpretation.

    File: backend/app/services/operation_executor.py — _build_command() uses f-strings with shell=True

  • CRITICAL-03 FusionSphere Adapter SSL Verification Disabled P0 · TLS/MITM

    The FusionSphere REST API adapter in platforms/fusionsphere/adapter.py configures the httpx client with verify=False, disabling SSL/TLS certificate verification. This allows any attacker positioned between the application and the FusionSphere endpoint to perform man-in-the-middle attacks, intercepting authentication credentials, VM migration data, and all administrative commands.

    Impact: Complete compromise of FusionSphere platform communication. Given the migration engine transfers VM configurations and potentially credentials between platforms, this is a severe data exposure risk.

    File: backend/app/platforms/fusionsphere/adapter.py — httpx.AsyncClient(verify=False)

  • CRITICAL-04 Unauthenticated API Endpoints (Missing CurrentUser) P0 · Access Control

    Multiple GET endpoints across alerts.py, assets.py, and operations.py router files lack the CurrentUser dependency injection. This means these endpoints are accessible without any authentication, exposing operational data including all registered assets, alert configurations, and operation definitions to unauthenticated callers.

    Impact: Unauthenticated access to internal infrastructure data. Attackers can enumerate all managed hypervisors, VMs, storage volumes, networks, and alert rules without credentials.

    Files: backend/app/routers/alerts.py, backend/app/routers/assets.py, backend/app/routers/operations.py

  • CRITICAL-05 Audit Middleware Body Consumption Bug P0 · Data Integrity

    AuditMiddleware.dispatch() reads request.body() for mutating HTTP methods (POST, PUT, PATCH, DELETE) before calling call_next(request). In ASGI/Starlette, the request body is a single-use stream. Once consumed by the middleware, it is empty when the actual route handler attempts to read it. This causes every mutation endpoint (POST/PUT/PATCH/DELETE) to receive an empty request body, silently breaking all create, update, and delete operations across the entire API.

    Impact: This is a showstopper bug. All mutation endpoints are broken. POST requests to create platforms, assets, or operations receive empty bodies and either fail silently or create records with only default values.

    File: backend/app/middleware/audit.py — dispatch() method, body consumed before call_next()

  • CRITICAL-06 No JWT Token Type Validation P0 · Auth

    JWT tokens issued by the platform include type: "access" and type: "refresh" claims, but decode_token() in security.py does not validate the type claim. This means a refresh token (which typically has a longer lifetime and different revocation semantics) can be used interchangeably with an access token for all authenticated API calls.

    File: backend/app/core/security.py — decode_token() function

  • CRITICAL-07 Migration Engine Commands Are Descriptive Strings P0 · Functionality

    The cross-platform VM migration engine generates command objects that are descriptive strings describing what should be done, but these commands are not actually executable. They are marked as "is_descriptive" rather than containing real, runnable instructions. The migration engine is effectively non-functional — it documents migration intent without performing any actual migration work.

    File: backend/app/services/migration_engine.py

Critical Runtime Errors

Additional P0 issues affecting runtime behavior and error handling

  • RUNTIME-01 Error Message Duplication in Token Validation P0 · Observability

    decode_token() in security.py catches JWTError and re-wraps it with "Token validation failed: {exc}". The caller in dependencies.py catches this new exception and wraps it again with the same prefix. The resulting error message to the client becomes "Token validation failed: Token validation failed: <original error>", which is confusing and leaks internal error details.

    Files: backend/app/core/security.py, backend/app/core/dependencies.py

Backend Code Review

P1 high-priority backend issues and architectural concerns

  • BACKEND-01 Dual Platform Enum Types P1 · Data Model

    Two separate enum types represent the same concept: asset.py defines Platform with mixed-case values (OpenStack, Kubernetes, Physical, Other) while platform.py defines PlatformType with lowercase values (vsphere, kvm, fusionsphere). These inconsistent representations create confusion and potential bugs when mapping between layers. The schemas are also mismatched with the database schema, where platform_type uses underscored variants (vmware_vsphere, fusion_sphere) that differ from application code (vsphere, fusionsphere).

    Files: backend/app/models/asset.py, backend/app/models/platform.py, db/schema.sql

  • BACKEND-02 No Alembic Migration Configuration P1 · DevOps

    Alembic is listed in requirements.txt but no alembic.ini configuration file was found in the project. The migration file db/migrations/001_initial.py exists but may not be integrated with the Alembic autogenerate workflow. Without proper migration tooling, schema changes cannot be reliably tracked, versioned, or rolled back.

    Files: backend/requirements.txt, missing: alembic.ini

  • BACKEND-03 In-Memory State Without Persistence P1 · Resilience

    ChatService stores conversation contexts in an OrderedDict with TTL-based eviction. OperationExecutor._running tracks in-flight operations in a plain Python dict. Both are lost on process restart, container redeployment, or horizontal scaling. Despite having Redis 7 available, neither service uses it for state persistence. This means chat context is lost on restart and running operation tracking fails across deployments.

    Files: backend/app/services/chat_service.py, backend/app/services/operation_executor.py

  • BACKEND-04 N+1 Query in DashboardService.get_summary() P1 · Performance

    DashboardService.get_summary() makes 7 separate repository calls sequentially instead of using asyncio.gather() to execute them in parallel. Since each call is an independent database query, the total latency is the sum of all 7 queries rather than the maximum of any single query. Under load, this adds unnecessary latency to the dashboard, which is typically the most-accessed endpoint.

    File: backend/app/services/dashboard_service.py — get_summary()

  • BACKEND-05 Module-Level Singletons Tied to Import Time P1 · Testability

    chat_service, operation_executor, and the migration engine are instantiated at module import time as module-level singletons. This makes unit testing difficult (cannot inject mocks without patching), creates fragile initialization ordering dependencies, and makes configuration changes require a full restart. These should use FastAPI's dependency injection system or a proper application factory pattern.

    Files: backend/app/services/chat_service.py, backend/app/services/operation_executor.py, backend/app/services/migration_engine.py

  • BACKEND-06 Response Model Inconsistency in Platform Service P1 · API Contract

    platforms.py _to_response() method does not include extra, created_at, or updated_at fields in the response object. The database model includes these fields but the API response silently drops them. This creates an incomplete API contract where clients cannot access metadata or creation timestamps.

    File: backend/app/routers/platforms.py — _to_response()

  • BACKEND-07 Stub Implementations Return 200 with success=false P1 · API Design

    AssetService.execute_action() and several compute operation endpoints return HTTP 200 with a JSON body containing success: false instead of returning HTTP 501 Not Implemented. This misleads clients into thinking the operation was processed but failed, rather than understanding the endpoint is not yet implemented.

    Files: backend/app/services/asset_service.py, backend/app/routers/compute.py

  • BACKEND-08 Missing API Routes for Implemented Services P1 · API Coverage

    OperationService.execute_operation() and OperationService.rollback_operation() have full service-layer implementations but no corresponding API routes exist. The functionality is implemented but unreachable through the REST API, representing dead code at the service layer and a missing feature at the API layer.

    Files: backend/app/services/operation_service.py, backend/app/routers/operations.py

Frontend Code Review

P1 high-priority frontend architectural and UX issues

  • FRONTEND-01 Dual Source of Truth: React Query + Zustand P1 · Architecture

    Platform data exists simultaneously in both the React Query cache (via usePlatforms()) and the Zustand store (platformStore). Migration status has the same duplication pattern. This dual source of truth is the most significant frontend architectural concern: it creates cache invalidation complexity, increases the risk of stale or inconsistent UI state, and makes debugging data flow significantly harder. Zustand should either be the single source of truth (with React Query for server sync only) or eliminated in favor of React Query's built-in cache management.

    Files: frontend/src/stores/platformStore.ts, frontend/src/hooks/usePlatforms.ts, frontend/src/stores/migrationStore.ts

  • FRONTEND-02 Dead Code: providers.tsx P1 · Maintainability

    app/providers.tsx duplicates the QueryClientProvider setup from App.tsx but is never imported or referenced anywhere in the codebase. This dead code causes confusion during development and could lead to bugs if someone imports it expecting it to be the canonical provider setup.

    File: frontend/src/app/providers.tsx

  • FRONTEND-03 Error Boundary Destroys Query Cache P1 · Resilience

    App.tsx wraps ErrorBoundary around QueryClientProvider. If the error boundary catches an error, the QueryClientProvider is unmounted, destroying the entire React Query cache. This turns a single component error into a full application cache loss, causing all in-flight queries to be cancelled and all cached data to be discarded. The error boundary should be placed inside the QueryClientProvider.

    File: frontend/src/App.tsx

  • FRONTEND-04 Chat Error Handling Is Silent P1 · UX

    useChat.ts handles errors by only calling setLoading(false). The optimistic user message remains displayed in the chat UI with no error indicator, no retry option, and no feedback to the user that their message failed to send. This is a silent failure mode — users will believe their message was processed when it was actually dropped.

    File: frontend/src/hooks/useChat.ts

  • FRONTEND-05 Missing 404 Route P1 · Routing

    router.tsx has no wildcard (*) / 404 route. Navigating to an unknown path renders a blank AppLayout with no child content, providing no indication to the user that the page does not exist. This is a basic routing completeness issue.

    File: frontend/src/router.tsx

  • FRONTEND-06 useCallback Dependency on Mutation Object P1 · Performance

    In useChat.ts, the send function is wrapped in useCallback with a dependency on the entire mutation object. Since mutation is a new object reference on every render, send is recreated on every render, completely defeating the purpose of useCallback. The dependency should be narrowed to the specific stable values needed.

    File: frontend/src/hooks/useChat.ts

Medium Priority Issues

P2 issues that should be addressed in the next development cycle

  • MED-01 Inconsistent Authentication on Read Endpoints P2 · Security

    Some GET endpoints require authentication while others do not, with no clear policy or documentation explaining which is which. This inconsistency makes the security posture unclear and could lead to accidental data exposure.

  • MED-02 No Request Timeout on Frontend HttpClient P2 · Resilience

    The frontend HTTP client has no AbortController / signal support for timing out requests. Long-running API calls can hang indefinitely with no user feedback or cancellation mechanism.

    File: frontend/src/lib/httpClient.ts

  • MED-03 No URL-Persisted Filter State P2 · UX

    Filter and search states live only in Zustand stores and are not reflected in URL query parameters. This means filters are lost on page refresh, cannot be shared via URL, and browser back/forward navigation does not restore filter state.

  • MED-04 Inconsistent ID Types P2 · Data Model

    Platform.id is typed as number while all other entity IDs (Asset.id, Alert.id, Operation.id) are typed as string (UUIDs). This inconsistency forces type guards and special cases throughout the codebase.

  • MED-05 No Input Sanitization on Chat Messages P2 · Security

    User chat messages are used directly in regex pattern matching without length limits or sanitization. A malicious user could send extremely long messages to cause ReDoS (Regular Expression Denial of Service) via catastrophic backtracking.

  • MED-06 Hardcoded Partition Dates P2 · Maintainability

    Migration partition creation uses hardcoded date ranges from 2026-01 to 2027-06. After July 2027, new partitions will not be created, and operations will fail. This should use dynamic date range generation.

  • MED-07 Alert Metric Values Stored as Strings P2 · Data Model

    Alert.metric_value and Alert.threshold are defined as String(100) instead of Float or Numeric. Numeric comparisons and aggregations in queries require casting, which prevents index usage and degrades query performance.

  • MED-08 Missing eslint in Frontend devDependencies P2 · Tooling

    The package.json defines a "lint" script referencing eslint but eslint is not listed in devDependencies. The lint script will fail on any machine that doesn't have eslint installed globally.

  • MED-09 Missing Platform SDKs in requirements.txt P2 · Dependencies

    pyvmomi and libvirt-python are listed as required platform SDKs but are not present in requirements.txt. A fresh install will fail when vSphere or KVM adapters are used.

Test Coverage Assessment

Strengths: All 246 existing tests pass. The test suite covers core service logic and API router behavior well. The use of pytest with async support (pytest-asyncio) is appropriate for the async SQLAlchemy architecture.

Critical Gap: There are zero integration tests for platform adapters against real hypervisor endpoints. Architecture Deep Dive

Detailed analysis of key architectural patterns, components, and their interactions

Adapter Pattern — Multi-Platform Virtualization

The platform adapter layer implements a clean Strategy Pattern (described as Adapter Pattern in the codebase) to abstract three distinct virtualization platforms behind a unified interface. Each adapter (vSphere, KVM, FusionSphere) translates the platform-agnostic operation definitions into platform-specific API calls.

Dependency Injection System

FastAPI's Depends() is used throughout for dependency injection. get_db() provides async database sessions, get_current_user() provides authenticated user context, and service classes receive their dependencies through constructor injection. This is well-implemented for the database and auth layers.

Gap: The chat service, operation executor, and migration engine bypass this system entirely, using module-level instantiation instead. This creates an inconsistent approach to dependency management and complicates testing.

Async/Await Pattern Usage

The codebase correctly uses async/await throughout the data access layer with SQLAlchemy 2.0's async session. FastAPI route handlers are properly declared as async def, and the async session is managed through a dependency that handles session lifecycle (open, commit/rollback, close).

Gap: DashboardService.get_summary() makes sequential await calls instead of using asyncio.gather() for parallel execution of independent queries, adding unnecessary latency.

Chat Service Architecture Analysis

Deep-dive into the regex-based intent recognition system and conversation management

Chat Service Concerns
  1. Regex Complexity: 97+ patterns with no organization by category or priority. Pattern matching is linear O(n) across all patterns, which combined with no input length limit creates a ReDoS vulnerability surface.
  2. Context Loss: Conversation contexts stored in OrderedDict with TTL are lost on any process restart. In a containerized deployment (Docker/K8s), this means every redeployment wipes all active conversations.
  3. No Intent Confidence Scoring: The system uses first-match-wins pattern matching. When multiple patterns could match, there's no confidence scoring or disambiguation mechanism, leading to unpredictable intent selection.
  4. Module-Level Singleton: The chat service is instantiated at module import time, making it impossible to configure differently for different environments or inject mock dependencies for testing.
